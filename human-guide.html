02

Why clones need repair

The pipeline records a video of a real website, decomposes the DOM into snapshots, and assembles those snapshots into React components. Each step has limitations that produce predictable bugs.

The pipeline, and what each stage leaves behind

RECORDER One path only Captures one session and only the clicked states. Closed components keep display: none; nothing has click handlers.
DECOMPOSER Compressed states Collapses snapshots into {state >= N} guards, splits lists into templated files, and misses the global :root block.
ASSEMBLER No interaction model Reassembles snapshots into React without understanding the interaction model behind them.
RESULT Predictable bugs Every clone carries a mix of these — not random bugs, but consequences of how the pipeline works.

The recorder captures one path

One user session, one set of clicks. Everything not clicked is frozen in its default state. Components captured in their closed position have display: none or collapsed CSS classes baked into the JSX. Every interactive element starts without click handlers.

The decomposer compresses snapshots

It compresses multiple snapshots into one page using {state >= N && state < M} guards. These numeric conditionals are compression artifacts, not interaction logic. When the decomposer captures a user navigating a calendar through three months, it produces many separate frozen item components instead of one programmatic calendar. When it captures a carousel auto-rotating, it produces multiple state-gated blocks for a few actual slides, some duplicated. When two snapshots capture the same element, it gets two overlapping state blocks and renders twice.

The decomposer also processes list items individually. A dropdown with 40 airports becomes 40 separate files, all templated from the first item. The first item's icon class gets hardcoded into every item — every country shows the same flag, every seat type shows the same color, every progress step shows as active.

The decomposer misses the global :root CSS block, so custom properties like var(--brand-color-primary) evaluate to nothing. Colors, borders, z-index, and border-radius are all slightly wrong.

The assembler doesn't understand interaction models

It can't tell that outbound and inbound calendars are actually one widget, or that a modal must be dismissed before the page is usable.

Every clone you open will have some combination of these issues. They are not random bugs — they are predictable consequences of how the pipeline works.

03

What Claude already knows

Claude's workspace is pre-configured with a CLAUDE.md that teaches it the evidence hierarchy, the repair phases, and the "hunt for siblings" instinct. It has a /diagnose skill for identifying issues, a /watch skill for sending video clips to Gemini, and access to the repair playbook and golden clones. You should not need to teach Claude these concepts from scratch.

What you should see Claude doing on its own

  • Checking the build before and after fixes
  • Reading video skeleton snapshots by rrweb ID (not guessing at CSS)
  • Scanning for sibling instances after fixing a pattern
  • Consulting the repair playbook when it hits a known pattern
  • Consulting golden clones before building complex widgets
  • Replacing numeric state >= N guards with semantic booleans
  • Creating and updating a REPAIR-LOG.md

Your eyes matter

Claude handles the detail work — comparing DOM structure, extracting CSS classes, matching against video skeletons — and gets most of it right. You're not doing pixel-by-pixel comparison. You're glancing at the page and flagging anything that jumps out: "the date is still missing," "that card is a different height," "those icons are all the same." You don't need to diagnose why or propose a fix — just flag what you see, and Claude will trace it back to the evidence.

If Claude is not doing these things, it's drifting. A simple reminder is usually enough — you shouldn't need to explain why, since Claude has the directives and just needs a nudge back to them.

Resolution"did you check the video skeleton?" or "did you scan for siblings?"
04

The order of repair

Claude is configured to follow this order, but understanding it helps you recognize where you are in the process and when Claude skips a step.

Build→Orient→Gate→Mechanics→Wiring→Cross-cutting

  1. Build

    Claude should check the build first. If it starts editing components without confirming the clone compiles, stop it.

    Resolution"does it build?"

  2. Orient

    Claude should look at the page and identify what's broken before fixing anything. If you see it jump straight to editing a component without reading the manifest or checking screenshots, it skipped orientation.

    Resolution"what does the page look like right now? run /diagnose"

  3. Gate

    Some pages have a modal or overlay that blocks everything; Claude should identify and fix this first. On Aer Lingus, a country/airport modal blocked the entire page — nothing else was testable until it was dismissed.

    Resolution"start with the modal — nothing else works until it's dismissed"

  4. Mechanics before wiring

    Claude should get components working in isolation (dropdowns open/close, carousels rotate) before wiring them to shared state. Mechanics first, then consequences. If it's trying to propagate a selection to the header before the dropdown even opens and closes, it's doing things out of order.

    Resolution"don't wire the consequences yet — just get it opening and closing"

  5. Frozen widgets

    Claude will identify components made of many frozen snapshot files and propose replacing them. Watch for two things: did it check the golden clones first, and did it check the video for the interaction model? On Aer Lingus, Claude built two separate calendar widgets; the user corrected — "the calendar won't close and reopen" — and the video showed one persistent widget.

    Resolution"did you check the golden clones?" / "check the video for how this actually behaves"

  6. Domain context

    Once the first page is alive and building, Claude should set up the domain context — the nervous system that tracks both cross-page data (origin, dates, passenger name) and per-element interactions (which dropdown is open, which card is expanded). Name it after the domain category: BookingContext for travel, ShoppingContext for e-commerce. Every interaction it wires then carries a tracking obligation — not just "make the dropdown open" but "make it open and track that it opened so the oracle can verify."

    Resolution"run /context"

  7. Cross-cutting lift

    Claude should defer removing all useEffects and lifting window APIs to a single pass at the end. If it tries to do this mid-repair on individual pages, redirect it.

    Resolution"lets finish first and finish by lifting all the window apis"
05

How to correct Claude during repair

Claude guesses instead of checking

You'll see Claude propose a CSS fix without referencing a video skeleton, or invent a class name that sounds right but doesn't exist. On Aer Lingus it used flight-search-card__selected-fare — a plausible BEM name that existed nowhere in the captured CSS. The skeleton had ei-result-card--selected.

Resolution"when you propose a fix, it must come exactly from a video skeleton — rrweb id 1410 in step-01-snapshot.html"

Claude fixes one instance and stops

The same-list bug appeared three times on Aer Lingus — country dropdown flags, progress bar active states, seat legend colors. Claude fixed each one only when pointed to it separately. It never proactively scanned for siblings. Say this every time; expect to repeat it for the first few sessions.

Resolution"did you check for the same pattern in sibling components?"

Claude infers flow from screenshots

Static video skeletons show states, not transitions. They can't tell you whether a calendar stays open between departure and return selection, whether a modal fades or snaps closed, or what auto-triggers after a selection. On Aer Lingus, Claude built two separate calendars because the screenshots showed two states; the video showed one persistent calendar.

Resolution"check the video for how this actually behaves" or give a range: "look at 1:20 to 1:45"

Claude declares victory without verifying

Claude will say "fixed" after editing code. On Aer Lingus it asserted a date fix worked — "Two fixes applied. The departure date should now display correctly." The user sent two side-by-side screenshots proving the date was still missing.

Resolution"does the rendered output match step-NN.png?" or "did you run the build?"

Claude uses the wrong evidence source

Each problem type has a best source. On Aer Lingus the user corrected this twice: "when you propose a fix, it must come exactly from a video skeleton" (Claude was guessing CSS from general knowledge), and "the video skeleton won't be helpful here, reference the original rrweb data" (wrong source for overflow styling). Point Claude at the right source — see the table below.

Resolution"which source answers that question?"

Claude leaves hardcoded values that should come from state

After the domain context exists, Claude will wire some fields but leave others hardcoded. On Aer Lingus the user had to audit every page: "the top header needs to pull from the context," "are we tracking the price," "identify every single hard coded thing that should be pulled from the context."

Resolution"is that value hardcoded or coming from the context?" or "run /wire on this page"
